Product Forge — Concept & Mental Model

Audience: new contributors and any agent/maintainer touching this repo. Goal: the 10-minute mental model — what Product Forge is, why it's shaped the way it is, and the producer→consumer map that makes the whole thing hang together. For a worked run see §6; for the rules see the normative four (§3).

1. The one thing to understand

Product Forge is "spec-as-product". It is not an application — there is nothing to compile or run. The deliverable is a process expressed as prompts: 33 markdown command files that instruct an LLM to perform one phase each, plus normative docs they defer to, plus a few zero-dependency Node helpers that make the load-bearing checks deterministic.

It ships from one repo in two forms (identical workflows):

FormManifestCommand syntax
SpecKit extensionextension.yml/speckit.product-forge.<name>
Claude Code / Claude plugin.claude-plugin/plugin.json/speckit-product-forge:<name>

Why it exists. Vanilla SpecKit starts from a written spec.md (spec → plan → tasks → implement). Product Forge wraps a full product lifecycle around that core — problem validation, research, an approved product spec, and a revalidation loop before spec.md; pre-impl review, progressive verification, code review, full traceability verification, Playwright E2E, release-readiness, and a retrospective after. The payoff is one unbroken traceability chain:

problem → research → product-spec → spec.md → plan → tasks → code → tests → metrics

with a human gate at every transition.

2. Why the codebase looks the way it does

The product's correctness IS the internal consistency of ~140 documents. There is no type-checker proving the spec coheres, so a contradiction between two docs is a silent runtime bug: the LLM reading them picks one interpretation and acts on it. Two recurring failure modes follow directly from this:

  1. "Callout-deep, not procedure-deep." A prose callout announces a capability ("the a11y gate is configurable", "the risk script routes the gate") while the step / carrier field / producer that actually executes it was never wired. The happy path reads like it works; it doesn't run end-to-end.
  2. Drift. A count, enum, version, or phase-map row is updated in one doc and not the other six that restate it.

Both are why this repo invests in deterministic self-checks rather than trusting prose review:

ScriptGuards against
scripts/lint-docs.jsdrift + callout-deep: dangling refs, plugin-root escapes, command-count / version / phase-map / enum parity, dead config switches, bare script paths
scripts/validate-traceability.jsthe structural half of the traceability chain (every must-have row reaches a task/code/test, no orphan task, P0/P1 edge coverage)
scripts/gate-risk.jsdeterministic gate risk class (so routing isn't an LLM vibe)
scripts/build-catalog.js / retrieve-catalog.jsthe _portfolio/catalog.yml carrier and deterministic retrieval over it (agents read one index instead of every folder)
scripts/cost-report.jsstatus --cost roll-up of per-phase token counters
acquire-lock.sh / release-lock.shthe .forge-status.yml state lock, invoked by the status-write procedure (runtime.md §2.9)
scripts/doctor.jsthe aggregate gate — runs every --selftest + lint-docs + fixture smokes + the release-blocking invariants. Run this first.

Honesty line: deterministic = structural. "Is this acceptance criterion truly measurable?" stays LLM-judged. The scripts front the LLM layers; they don't replace them.

3. Read these four, in this order

The command files are thin; the rules live in the normative four. When command prose and a normative doc disagree, the doc wins.

Listed in precedence order — when two of them disagree, the earlier one wins.

  1. runtime.md — orchestration: the 5-layer config merge, ${PLUGIN_ROOT} script resolution (§1A), the state lock and the status-write procedure (§2.9), resume logic, sync-verify integration, gate ownership and the gate prompt (§6), phase digests, per-mode phase prerequisites (§11.2), the Path-Resolution Contract (§12).
  2. policy.md — the rules: gate decisions, feature modes (express / lite / standard / v-model), skip policy, role approvals, the gate-review surface.
  3. schema.md + schema/forge-status-v3.schema.yml — the canonical .forge-status.yml v3 shape and the cross-artifact ID system (§8). The .yml file is authoritative when the narrative differs.
  4. file-structure.md — the per-feature artifact tree, storage strategies, and naming conventions.

State for every feature lives in one file: <FEATURE_DIR>/.forge-status.yml.

5. How to make a change without breaking the spec

  1. Run node scripts/doctor.js — establish a green baseline.
  2. Make the edit. If it touches a count, enum, version, phase-map row, config key, or a bundled-script invocation, expect lint-docs to have an opinion.
  3. Run node scripts/doctor.js again — it must stay green. lint-docs must report 0 error-severity findings.
  4. If you added a config key, a command must read it (CONFIG-READER rule) — a documented-but-unread key is the a11y_gate dead-switch class — and a key the docs tell users to set must exist in config-template.yml (CONFIG-DECLARED).
  5. If you added a script call in a command, route it through ${PLUGIN_ROOT} (runtime.md §1A), never a bare node scripts/... (SCRIPT-PATH rule).
  6. Bump the version in both extension.yml and .claude-plugin/plugin.json together, and add a CHANGELOG.md entry.

CI (.github/workflows/ci.yml) runs doctor on every push and PR — it is the automated version of step 3.

6. End-to-end walkthrough

A greenfield standard-mode feature, happy path:

  1. /speckit.product-forge.forge Build push-notification preferences — forge triages the change and recommends a track (here standard), resolves FEATURE_DIR via the Path-Resolution Contract, and creates the v3 status file from the initial document (schema.md §3.1).
  2. Phase 0 (optional) problem-discovery → gate → gates[] entry, phases.problem_discovery.status: completed, digest at problem-discovery/digest.md.
  3. Phase 1 research pulls matching lessons from .product-forge/lessons.md; Phase 2 product-spec writes journeys (JRN-*) and stories (US-*); quick sync-verify runs at each transition (auto_sync_between_phases).
  4. Phases 3–5B revalidation, bridge (spec.md, FR-*, contracts), plan, tasks (each task carries Paths:). 5.5 migration-plan runs only when the plan has a data-model change; 5C pre-impl-review is optional.
  5. Phase 6 implement: per task, write code, commit, append task_log[] through the status-write procedure (lock → merge → atomic rename); progressive verify every N tasks; red_gate records the test-first check.
  6. Phases 6B → 7 → 8A → 8B code review, verify-full (11 layers), test plan and Playwright run — each behind a gate whose options are computed (runtime §6.3).
  7. Phase 9 release-readiness, then optional 9.5 monitoring, 9B experiment design, 10 spec-merge into canonical specs/.
  8. Retrospective (≥14 days post-launch) compares research/metrics-roi.md to actuals and appends lessons.

In lite the same run is product-spec → plan (with an inline ## Tasks list) → implement → verify; express is the minimal version of that.

Honest limits. Every rule is an instruction to an LLM: the lock, digest and gate rules are best-effort where a host cannot run the helper scripts. Product Forge generates monitoring/flag/dashboard artifacts but does not push them to providers; i18n-harvest writes stubs, not translations; portfolio and feature-flag-cleanup are read-only.

8. Glossary

The shared vocabulary of commands and docs. Commands use these words without re-defining them.

TermMeaning
phase / phase keyOne lifecycle step (Research, Plan, …); its snake_case key (product_spec) names its block under phases. in .forge-status.yml. The set per mode is schema/phase-map.yml.
feature modeexpress · lite · standard · v-model — which phases run (policy.md §4).
flow modegated (one phase at a time, gate after each) or fluid (any phase in the runnable set).
gateThe human decision after a phase: approved · approved_with_conditions · revised · skipped · rolled_back · aborted, recorded in gates[] (runtime.md §6). Gate extras are the phase-specific fields on that entry.
standalone / --from-forgeHow a command runs: on its own (it shows and records its gate) or under the forge orchestrator (it returns its outcome; forge shows the single gate).
effective configThe merged five-layer config (runtime.md §1).
command contractThe rules every command follows (runtime.md §0).
carrierA file one phase writes so a later phase reads one small, structured input (traceability.yml, journeys.yml, _portfolio/catalog.yml, a named report section).
digestThe short summary a phase writes before it completes; later phases read digests before full artifacts (runtime.md §8).
driftTwo artifacts (or an artifact and the code) that should agree but do not. Each layer of sync-verify / verify-full checks one such pair.
canonical spec / delta specspecs/<domain>/spec.md is how the system behaves now; a delta spec lists one change's ADDED / MODIFIED / REMOVED requirements and is folded in by spec-merge.
index / partThe halves of a document split under the size budget; a single-file document is one a later step reads by name, so it is tightened instead of split (runtime.md §10.1).
red gateThe test-first checkpoint inside implement: a Must-Have story's tests exist and fail before its code is written.
runnable setThe phases a fluid feature may run next: prerequisites met and in scope for the mode (runtime.md §11).
FEATURE_DIR / ${PLUGIN_ROOT}The resolved feature folder (runtime.md §12) and the installed plugin root (runtime.md §1A).
