spec-kit-ado

Spec-driven development for Azure DevOps teams, with a person approving every change an agent makes. Pull a story into a per-story ledger that ties each acceptance criterion to a named test, let your AI agent do the work through Spec Kit, and see the exact Azure Boards or pull request change before it is applied, and only after you say yes. Works with Azure Repos or GitHub. Community project: not an official GitHub or Microsoft product.

A Spec Kit extension and a small ado CLI that run the whole Spec Kit loop from an Azure DevOps (ADO) story back to Done, with a person in the loop by construction. When the agent or the ado-lifecycle workflow drives the lifecycle, every board change is previewed and applied only after a person approves it (in the workflow, every ADO change and PR is a preview step, a human gate, then an apply step), and the CLI's batch verbs are dry runs unless given --apply. (Single CLI verbs such as ado update act immediately when a person runs them, and the CI templates act after a merge only as the repo owner configures them.) Every acceptance criterion is traced to a named test in a per-story ledger. The gate reports problems first and only blocks the checks you opt in to. Specify, plan, tasks and implement are handed to whichever Spec Kit stack kit you have installed (or to core Spec Kit), so the extension works for any tech stack.

Azure DevOps Boards only (Azure Repos or GitHub for code); Jira and GitHub Issues are not supported. See docs/tracker-boundary.md for what the kit does and what stays in the tracker.

New here? docs/quickstart.md takes you from a story to pushed Tasks with the lightest setup (ado setup --profile starter; the commands that need no agent took about 10 seconds in a timed run, and the rest, you and your agent, is not timed); docs/glossary.md explains every word in one sentence. See it catch a faked "green" commit in a real run, with no Azure DevOps account: docs/demo.md. Running it with nobody at a terminal: docs/unattended.md. Which Spec Kit versions it was tried against: docs/compatibility.md.

Quick start

Requires Spec Kit 1.2.1 or later (the supported floor; nothing below it was tried, see docs/compatibility.md), Python 3.9 or later, and git. gh is needed only to open PRs on GitHub.

You also need the tools that install and run it. specify is the Spec Kit command-line tool: install it by following the Spec Kit README, then check specify --version. pipx (or uv) installs the ado command in its own environment: python3 -m pip install --user pipx is one way to get pipx (see the pipx docs). It was tried on macOS by hand and on Linux in CI. Windows: the package installs and ado --version starts on a Windows runner (checked once, 2026-11-07), but the test suite and strict mode (it runs your test command through /bin/sh in its own process group) are POSIX-only, and the PAT file has no Keychain or chmod 600 there (see the security notes below). On Windows use WSL.

There is no PyPI package, and the project is not listed in the Spec Kit community catalog yet, so install from GitHub with the commands below.

# 1. The ado CLI (stdlib only)
pipx install git+https://github.com/praveenlavu/spec-kit-ado@v0.3.2
# or: uv tool install git+https://github.com/praveenlavu/spec-kit-ado@v0.3.2

# 2. The extension, in your Spec Kit project
specify extension add ado --from https://github.com/praveenlavu/spec-kit-ado/archive/refs/tags/v0.3.2.zip

Install the bundle (workflow + extension)

specify extension catalog add https://raw.githubusercontent.com/praveenlavu/spec-kit-ado/v0.3.2/catalog/extensions.json --name ado --install-allowed
specify workflow catalog add https://raw.githubusercontent.com/praveenlavu/spec-kit-ado/v0.3.2/catalog/workflows.json --name ado
curl -L -o ado-0.3.2.zip https://github.com/praveenlavu/spec-kit-ado/releases/download/v0.3.2/ado-0.3.2.zip
specify bundle install ./ado-0.3.2.zip

Install-allowed catalogs install what they list without the untrusted-source prompt (workflow catalogs always are); these list only ado and ado-lifecycle from the v0.3.2 tag, so read them and workflow.yml first. Details: bundle README.

The Spec Kit community catalog is for discovery only, so a bare specify extension add ado does not install it; use --from as above. From a local checkout: specify extension add --dev <path-to-spec-kit-ado>.

Then, in your agent:

/speckit.ado.setup          # checks tools, asks you to run `ado setup`, confirms the phase map
/speckit.ado.pull 1001      # story 1001 -> dod/DoD_1001.md + spec

Commands are named speckit.ado.<verb> throughout these docs. How you type one depends on how Spec Kit installs it for your agent:

ado setup runs in your own terminal: it asks for the organization and project and reads a Personal Access Token through a hidden prompt. Scopes: Work Items: Read & Write and Project and Team: Read (ado setup and ado branch --link read the project record); add Code: Read for ado branch --link, and Code: Read & Write for ado pr create and ado pr comment on Azure Repos (on GitHub, PRs go through gh, so no Code scope). The token never passes through the agent chat.

To run the whole lifecycle with engine-enforced approval gates instead of command by command, add the workflow (the bundle describes the extension and the workflow as one unit):

specify workflow add --dev <path-to-spec-kit-ado>/workflows/ado-lifecycle
specify workflow run ado-lifecycle -i story_id=1001

In a workflow run, command steps make no ADO writes; the workflow's preview → gate → apply steps do. The steps, in order:

  1. pull (spec, ledger, and the story branch via ado branch --apply), then the review-spec gate.
  2. questions-loop: posts the ledger's open questions to the story as one comment (ado questions --post; a re-run edits it, and with none open the apply does nothing).
  3. plan, then plan-questions-loop (posts the owner: PO questions the plan raised; the same comment is edited), then the wait-po-answers gate, then plan-with-answers (plan again: reads the PO's replies into the ledger and revises the plan), then the review-plan gate; tasks. The run does not wait for the product owner by itself: wait-po-answers stays open until you approve it, so that is where you wait for replies (or approve to go on with the plan's stated assumptions).
  4. push-loop: creates or updates the child Tasks.
  5. strict-check-implement (strict mode: ado strict check --phase implement stops the run on exit 2), implement, then decisions-loop (posts the decisions recorded in Decisions_<id>.md as one new comment: preview, approve-decisions gate, apply), strict-verify (strict mode: ado strict verify) and sync-loop, which syncs the Task states ticked during implement. In an advisory project strict-check-implement and strict-verify are no-ops (exit 0, a note), and decisions-loop is a no-op when there is no decisions file; when there is one the post happens in every mode, behind the gate (--if-any makes a missing decisions file a no-op). strict-verify sets timeout: 7200 (the engine's 300 s shell default would kill the test runs).
  6. gate, then gate-check, a shell step that re-runs ado gate --base <default branch> with the PR's changed files and halts the run when a gate.block check fails (exit 1) or ado.config.json is invalid (exit 3).
  7. review, then the review-review gate.
  8. pr-clear, pr-prepare (speckit.ado.pr --prepare-only writes the PR body), then pr-loop: pushes the head branch and opens the PR. The last gate, wait-po-validation, is where you wait for the product owner to validate or reject the posted decisions (in terminal mode a human records each with ado decisions <id> --resolve; with approvers configured, --resolve is refused and ado decisions <id> --sync records the approvers' /approve D<n> and /reject D<n> comments; either way commit and push the recorded lines to the PR branch before the merge; in strict mode ado done refuses while any is open).

Every preview → gate → apply triplet (questions-loop, plan-questions-loop, push-loop, decisions-loop, sync-loop, pr-loop) is a do-while loop, and each apply applies only the plan its gate showed (--expect-plan). If the plan changed since approval, for example when you resume a failed apply after editing tasks.md, the apply exits 2 and writes nothing, and the loop stops after that one pass (max_iterations: 1) and the *-applied step after it ends the run FAILED (start a new run). It does not preview and ask again: a verdict supplied with --input stays set and would approve the changed plan unseen. The move to Active is not automated there: move the story yourself, or run speckit.ado.pull interactively. The workflow ends at the open PR; it never closes the story. Closing happens after merge: CI link-on-merge with close-story: true (closeStory: true on Azure Pipelines), or speckit.ado.done run by hand.

Upgrading from 0.2.0

0.3.0 removes no command and renames no config key, and its new features are all opt-in. It does change behaviour for existing users, though, with or without any new config key: the changelog lists eighteen such changes under "Advisory-mode additions in 0.3.0" (read all of it), and "Changed" lists the strict-mode ones. The ones a 0.2.0 user is most likely to notice:

  • Refusals instead of a pass (exit 2, or 3 for gate, before anything is sent to Azure DevOps): ado attach and ado done refuse a symlink, a file that is not a regular file and a file over 5 MiB, and done refuses a symlinked or over-1-MiB ledger; done, the five applies (questions --post, push, decisions --post, pr create, branch --link), decisions --resolve, approvals, and questions / decisions --sync read the target branch's config and stop on an unreadable or invalid one, on a dangling origin/HEAD, on trust keys (approvers, approval, unattended) in the working-tree config of a checkout without origin/HEAD, and on those keys in a config file that is not the repo-root ado.config.json (ADO_CONFIG, config-path); gate exits 3 on an invalid target-branch config when --base is given; done --base REF (new, and what the shipped CI close steps pass) exits 2 when REF is no commit here or names different approvers than origin/HEAD; a trust key already in your config now has to be valid (0.2.0 ignored it); a decisions line containing · via: is now malformed; and ado update --state <done_state> is refused in strict mode (use ado done).
  • Terminal-mode workflow runs and prompts stop earlier. The workflow runs approvals check and the two --sync --if-comment-mode steps in every mode, so a terminal-mode run on a checkout whose origin/HEAD dangles stops at its first check-* step; the speckit.ado.review and speckit.ado.pr prompts run ado pr create <id> --check-committed, so a terminal user who runs either outside the workflow stops there too.
  • A comment and a commit you did not get before. When a decisions file exists, the plan and implement prompts record decisions and the workflow posts them behind a gate in every mode, so the product owner gets a [spec-kit-ado:decisions] comment; the review step's one commit now also carries the spec directory, the decisions file and the story's rules files (the PR step's commit had them); new ledgers get a sentence pointing at Decisions_<id>.md; gate and done add decisions fields, and done attaches the decisions file when it exists (its plan renumbers a step and makes a second attachment request).
  • Output and prompt text. The usage text lists the new verbs and flags; pr create --apply on GitHub passes the PR body to gh on stdin; ado setup shows an existing value of about 79 characters or more, a secret-looking one or one with non-ASCII characters JSON-quoted or as "existing value, too long to show" instead of echoing it; text read from ADO is scrubbed in linear time, with over-long addresses cut; speckit.ado.status starts with ado status <id> and speckit.ado.setup suggests ado setup --profile starter.

What is new, all opt-in. New verbs: doctor (checks the setup and prints a fix per row), status (the stage and the next command), approvals, decisions, strict, stack, kits, rules and calibrate. Strict mode ("mode": "strict"), stack profiles and pinned kits, business rules, comment approvals ("approval": "comment" with approvers) and the unattended poller (unattended) do nothing until you configure them.

Floors. Spec Kit 1.2.1 or later (the supported floor; 0.2.0 declared 0.9.0 and nothing below 1.2.1 was tried) and the ado CLI 0.3.0 or later (the extension's commands call status, doctor and --sync). Python 3.9 or later, as before. With a Spec Kit older than 1.2.1, specify extension add refuses the 0.3.0 extension (the 0.2.0 one you have installed keeps running) and ado doctor shows fail on its specify row whatever extension is installed.

Run ado doctor after upgrading. It covers part of the list above only: its config-target and approvers rows show an unreadable target-branch config or a dangling origin/HEAD, and specify shows the floor; it has no row for symlinked or oversized files, attachments or decisions lines, so those show up as the refusals described above.

History. 0.2.0 was tagged only on the private repository and has not been released publicly, so the @v0.2.0 URLs below do not resolve for anyone else yet. These steps are for people who installed 0.1.1 from an earlier copy of this project; 0.2.0 users read the section above.

0.2.0 changes behaviour for existing users: read the Breaking list in the changelog first. Then, in each project:

  1. CLI. Reinstall from the release tag: pipx install --force git+https://github.com/praveenlavu/spec-kit-ado@v0.2.0 (or uv tool install --force git+https://github.com/praveenlavu/spec-kit-ado@v0.2.0). The 0.2.0 extension requires ado 0.2.0 or later, so do this first.
  2. Extension. Replace the installed one: specify extension add ado --force --from https://github.com/praveenlavu/spec-kit-ado/archive/refs/tags/v0.2.0.zip.
  3. Workflow, if you use it: specify workflow remove ado-lifecycle, then add it again (specify workflow add --dev <path-to-spec-kit-ado>/workflows/ado-lifecycle from a v0.2.0 checkout, or specify bundle install as above). Start new runs with the new workflow: it has new steps and gates.
  4. CI consumers. @v0 and toolkit-ref: v0 follow the latest v0.Y.Z tag. To stay on a reviewed version, pin the reusable workflows and the CLI they install: uses: praveenlavu/spec-kit-ado/.github/workflows/ado-gate.yml@v0.2.0 with toolkit-ref: v0.2.0 (GitHub), or ref: refs/tags/v0.2.0 on the spec-kit-ado repository resource (Azure Pipelines).
  5. Config. Keep your ado.config.json, but ado setup fills in only keys that are absent. A config copied from the 0.1.1 template already holds "done_state": "Done", which Agile (Closed) and CMMI projects do not have, so delete done_state (and any story_type or removed_state that is wrong for your project) first: grep -nE '"(story_type|done_state|removed_state)"' ado.config.json shows them. Then re-run ado setup: it adds the three from your project and keeps every other key. A new optional key is branch_prefix. review_block_on is not new, but 0.2.0 starts enforcing it (ado pr create refuses on a matching review finding) and validating it, like gate.block and gate.tests, so a mistyped name is now an error. See docs/configuration.md.
  6. Ledgers. For each story in flight run ado dod <id> --refresh: it re-pulls section 1 with the new escaping and keeps sections 2 to 5 (it also records the story's current acceptance criteria, so check AC drift first). Then give every AC in section 1 a row in section 3: the gate now counts the AC lines in section 1, and an AC with no row is unmapped. --refresh refuses a ledger with an unclosed code fence or comment, or without the ## 2. Brainstorm & plan heading; fix the file by hand, or use --force to start over (--force refuses while the ledger has a Rules reviewed: line: remove the line by hand first, knowing the removal is traced).
  7. Branches. CI recognises only <branch_prefix>ab<id>-<slug> (for example feature/ab1001-count-active-members) or AB#<id> in a branch name. Rename open branches with git branch -m.

Strict mode

With "mode": "strict" in ado.config.json, ado strict check <id> --phase implement refuses (exit 2, findings as JSON, each with the command that fixes it) until the spec dir has spec.md, plan.md and tasks.md, ledger section 2 has no _(fill in left in Approach, Assumptions or Use cases & edge cases, no question is open (an assumed: answer counts as closed), every task in tasks.md has a Task on the board (a board that cannot be read is a board-unchecked finding, never a pass) and strict.test_command is set. A minimal strict config is {"mode": "strict", "strict": {"test_command": "python3 -m pytest -q", "test_timeout": 300}}. The test command runs with the PATH of the environment that runs the check (put the toolkit venv first if your tests need it): a Mac has no python, so use python3.

In strict mode the shipped workflow's stack-check step (ado stack show --check) also needs an approved stack profile (ado.stack.json) whose test command matches strict.test_command; without one the run stops at stack-check (exit 2), so create and approve the profile before the first run (see docs/stack-kits.md).

The pr and done phases check L1 order evidence: every AC row of ledger section 3 must have red <sha> → green <sha> (or ->; 7 to 40 hex characters; backticks, bold and trailing words are tolerated) in its status cell, and the SHAs must be real. Work in two commits per AC: a red commit with only tests, then a green commit with the code. The check, run with GIT_NO_REPLACE_OBJECTS and a 30 s timeout per git call and needing a full clone (fetch-depth: 0 in GitHub Actions, fetchDepth: 0 in Azure Pipelines; a shallow one reports sha-unknown), refuses with evidence-missing (no pair, or an AC with no row), sha-unknown (not a single commit in the repo), merge-commit (red or green is a merge), red-not-ancestor (red is not an ancestor of green, or they are one commit), red-touches-code (red changes a file that is neither a test file nor one of exactly three: <dod_path>/DoD_<id>.md, <dod_path>/Decisions_<id>.md and <spec dir>/tasks.md, never a whole directory; the ledger's Spec dir: counts only when it is relative, has no .., is not dod_path or inside it and holds a regular-file spec.md or tasks.md in the tree; test files are the gate.tests globs plus the built-in ones), red-no-test (red adds or changes no test file) and green-not-on-branch (green is not an ancestor of HEAD). The story's ledger, its decisions file and the tasks.md tick may ride in the red commit. It proves order, not that the tests fail: ado strict verify runs them. Advisory mode (the default) is unchanged. See docs/configuration.md for mode and strict.

L2: ado strict verify <id> runs L1, then the test command at every AC's red commit (it must exit non-zero) and green commit (it must exit 0), once per distinct commit, and at HEAD (it must exit 0 there too, so a later commit that breaks the tests is refused as head-fails), with strict.test_timeout per run, and (default --record) writes the verification record into ledger section 4 (see the command table). A red commit whose tests pass, a green commit whose tests fail, a timeout, an unset strict.test_command and a checkout that fails are each refused with the AC named (red-passes, green-fails, head-fails, timeout, test-command, runner-error; exit 2). It cannot tell which AC a failure belongs to: it records pass or fail per run. ado strict check --phase pr|done never runs tests; it validates the record: record-missing, record-stale (the head moved past the recorded one by anything except the ledger, Decisions_<id>.md or tasks.md), record-incomplete (an AC without a line, no - head: line naming the recorded head, or recorded SHAs that differ from the section 3 status cell now) record-failed and record-command-mismatch (the record's command-sha256 is not the first 12 hex of the sha256 of the strict.test_command in force: the target branch's in strict CI, so a record made with a weaker command locally is refused; an unset command with a record present is the same finding; l2 covers it). The done phase validates the record without the ancestry and staleness rules, so it survives a squash merge. A fresh reviewer is shown only the AC text from ledger section 1 and the bodies of the tests mapped in section 3 (not the implementation, not the PR text) and rules per AC whether the test asserts the stated behaviour. How to answer a PO rejection. A rejected decision blocks pr and done (decision-rejected) and is never edited or deleted. (The one exception, with rules.enabled: a rejected out of scope: BR-… line that was posted and not re-worded since (its posted: marker matches). The rule it tried to lift is back in scope, so the rejection shows as rule-uncovered until an AC row cites the rule with a test; the line itself is neither deleted nor re-worded. ado gate leaves it out of open_decisions for the same reason.) When the work now follows the PO's answer, record a new decision that supersedes it: ado decisions <id> --add "<what you do now>" --kind decision --supersedes D3. The line reads D5: supersedes D3: <text>; the PO sees that prefix when you post it (ado decisions <id> --post, preview then yes: pr refuses with supersedes-unposted until it is posted). While D5 is not rejected, D3 no longer counts: pr passes, and done waits for D5 like any other open decision (the PO validates or rejects it, a human records that with --resolve). A rejected D5 re-activates D3 (decision-rejected names both); answer that with a new decision that supersedes D5 (a chain: the head that is not rejected answers every line below it). --supersedes takes a rejected decision, or an open one the PO has already seen (post it first; refused with post D<n> first otherwise), never a validated one or an override, and one live answer per decision. A decision that was never posted cannot be superseded (post D<n> first): the PO has not seen it, so it must be posted before it can be replaced. To replace a stale line that was never posted, post it and then supersede it, or ask the human; this is a known limit, there is no shortcut. Post a decision before superseding it: --supersedes refuses a target that is still unposted (post D<n> first), so the PO sees both the old line and the one that replaces it. Every line that supersedes another needs a posted: marker that matches it (its id is part of the hash, so a copied marker does not match), whatever its status: a real superseder keeps its marker when a human resolves it. That marker is only a claim in a local file and is never checked against ADO in this release: a hand-computed marker passes, so the control is the PO reading the posted comment (process enforcement, not a technical one). If two lines supersede the same target and one of them is rejected, that rejected line keeps blocking. ado decisions <id> --resolve on a decision that is already superseded still records the verdict and prints a notice (stdout JSON) that it is masked by the superseder. ado gate and open_decisions count the same effective set; in advisory mode a file without supersedes lines reads and prints exactly as before.

End of the flow. The workflow ends at the open PR; nothing in it ticks ledger section 5, so ado done reports the story not ready after the merge until that section is ticked. After the merge run /speckit-ado-done <id> (it ticks section 5 only with evidence, shows the plan, then closes the story), or tick section 5 by hand and commit it before CI close-story runs. In strict mode done additionally runs the strict done check. In strict mode set close-story: true: without it no strict done runs.

done after a squash merge: the red and green commits are no ancestors of the merged HEAD, so done runs no git ancestry or SHA lookup for them: from L1 it keeps only evidence-missing (every AC has a row whose status cell is a red <sha> → green <sha> pair), skips the staleness checks of the record and the review, and validates the record against the recorded SHAs instead (completeness, the section 3 status cells, the exit codes, one - head: line), so it works after the branch is deleted and its commits are garbage-collected. A detached HEAD (a CI checkout of the merged commit) is read as the commit it is; for pr a detached HEAD is refused (review-blocks), so CI passes the head commit: ado strict check <id> --phase pr --head <sha> --base origin/<target>. A section 3 commit/PR cell may hold PR head <sha>: that is optional, written by the agent, and can only add a refusal (the record must then be for that commit); leaving it out never helps or hurts.

Stack rules (implement, pr, done; see docs/stack-kits.md "Strict rules and CI"). A strict project needs an approved ado.stack.json (speckit.ado.stack drafts it, a human runs ado stack approve --apply): stack-profile-missing, stack-profile-invalid, stack-profile-draft, stack-profile-changed, stack-profile-drift and stack-unprofiled refuse with the fix, and none can be overridden (an unknown stack stops the run). In CI the profile, ado.kits.lock.json and strict.test_command come from the target branch, so a PR that edits them changes neither the command nor the verdict in that PR's own run; once merged the edit is in force with no note (an approved hash is computable by anyone), so review edits to these files as code. The PR's own profile is checked too (invalid, draft, changed, deleted or inconsistent with its strict.test_command is refused, detail "at the head commit"), and so is its ado.config.json: present but invalid (a tab or control character in strict.test_command, invalid JSON) is the finding config-invalid (a fixed text, no value echoed; not overridable). Process enforcement, not a security boundary.

Kit rules (implement, pr, done; see docs/stack-kits.md "Kit rules, local and CI"). kit-unpinned and kit-changed refuse an installed kit that no human pinned, or one that changed since (ado kits pin records the review, in a terminal); neither can be overridden. Local: ado kits verify over the registry, the kit dirs and the Claude agent copies. What CI checks and what runs locally: CI (a strict target config) judges the lockfile of the target branch against the files git tracks in each locked kit dir at the PR head, flags a newly tracked .specify/extensions/<dir>/extension.yml that the target lockfile does not pin, and treats a symlink or submodule entry in or in place of a kit dir as kit-changed; it does not read .specify/extensions/.registry, the agent copies (.claude/...), untracked files or <id>-config.yml, so an edited agent copy is caught on a developer's machine only. The toolkit's own ado extension (.specify/extensions/ado/) is no kit in CI either, as locally. Locally, a pinned kit whose registry entry is gone while its files remain is kit-changed only when the registry file exists (upstream says not to commit it, so a fresh clone sees nothing there). A PR that edits ado.kits.lock.json does not change its own verdict (it deletes or breaks it: refused). With no lockfile on the target the rules are a note, and the PR that adds the first one is flagged for review as code. Advisory mode only reports (ado kits verify). Process enforcement, not a security boundary: whoever can edit both a kit and the lockfile on the target branch can re-pin.

The toolkit's own files are not checked. A PR can rewrite .specify/extensions/ado/ (its commands, rules and templates are prompts the agent follows after merge), and neither CI nor ado kits verify checks that directory. For now, review it as code. CI still judges the results (evidence, tests, gates), so a hostile prompt alone cannot pass a PR. See docs/stack-kits.md "The toolkit's own extension is no kit"; a digest check is a candidate for v0.4.

Emergency override (ado strict override <id> <rule> --reason "<text>" --apply, in your own terminal): records a kind: override decision that lets exactly one rule pass for every check of the story until it is done: test-command, l2 (the record and test-run rules), open-question or placeholder. spec-missing, plan-missing, tasks-missing, evidence-missing, sha-unknown, every red-* rule, merge-commit, not-in-range, decision-rejected, the business-rules ids (rule-uncovered, rule-unknown, rule-unconfirmed, rule-changed, rules-problem, rules-missing, rules-format, rules-header) and the other L1 rules can never be overridden, and a rejected override covers nothing. The command refuses (exit 2) unless stdin is a terminal, which is a guard against accidents, not a security boundary: the decisions file is plain text, a pseudo-terminal gives a tty, and an agent can hand-write a line. What makes an override visible is that it must be posted to the story and so reach the PO before pr, and that it stays in git history; strict check lists the entries it used in overrides_used pr create --apply and done --apply stamp · used: <date> on those lines (decisions.stamp_used, written atomically and read back whole; the stamp is an uncommitted local change: commit the stamped decisions file; if that write fails the command exits 2 before it sends anything, and a refused run or a preview stamps nothing). The posted: marker is a hash in a local file: it is never checked against ADO in this release, so a hand-written marker passes. --reason may not contain an e-mail address or an @mention (exit 2), and a second override of a rule that already has one in force (not rejected) is refused. l2 also covers test-command, so one l2 override lets an unset strict.test_command pass. ado strict verify honours overrides like check: with an l2 or test-command override in force it runs no tests, records nothing and exits 0 with verification skipped: overridden (and overrides_used) (with --no-record, as in CI, an override in force is instead the finding override-in-force and exit 2 unless --allow-override is passed).

CI trust: the config comes from the target branch. With --base REF on gate, strict check, strict verify, strict mode and branch --id-from the command first reads ado.config.json from the PR's target branch (git show at the full ref, resolved as refs/remotes/REF, then refs/heads/REF, then a full 40-hex commit id, never a tag); when that file says mode: "strict", the whole run uses it and the PR's own ado.config.json is ignored for strictness (gate.block, gate.tests, dod_path, branch_prefix, review_block_on, strict.*), so a PR cannot weaken or re-point its own checks. A target with no config, or an advisory one, leaves the PR's config in charge, as before. A target config that is unreadable or invalid, or a git failure, is an error: exit 3 for gate, branch --id-from and strict mode (CI fails closed), 2 for strict check and strict verify. A REF that is no commit here (a shallow clone: use fetch-depth: 0) leaves the target unreadable: with a strict PR config it fails closed the same way, with an advisory one it is the v0.2 path (the gate notes that commits were not checked and never blocks on it). ado gate says which config judged the PR with one extra line in its summary and the JSON key config: config: target branch (strict) when the target's was used, config: pull request when --base was given and the PR's own strict config judged it; nothing is added otherwise. Stack profile and lockfile. Under a strict target the same read also takes ado.stack.json and ado.kits.lock.json from the target commit (each at most 256 KiB, regular files); an unreadable or invalid one (bad JSON, a duplicate key, the wrong schema, a secret-looking string, a control character) is the same error as an invalid config (exit 3 for gate, branch --id-from and strict mode, 2 for strict check and strict verify), with a fixed text that carries none of the file. When the target has no profile the PR that adds the first one must bring a valid, approved profile that matches its strict.test_command; any PR that edits the profile, the lockfile or strict.test_command is flagged trust-introducing PR: review ado.stack.json as code (in the strict check warnings and in the gate comment): review it as code, because what runs in CI is the merged strict.test_command, which ado stack approve sets. Once the target has a profile the rules bind, so a new root takes two PRs: the profile first, then the code. Protect ado.stack.json and ado.kits.lock.json on the target like ado.config.json. Limits, plainly. Only the repo-root ado.config.json is read from the target: with a non-default config-path (GitHub) or ADO_CONFIG no target file is found and the PR's config applies silently. The CI definition is itself PR-controlled (the GitHub caller workflow and its toolkit-ref, the Azure PR pipeline YAML) and the ledger and decisions file are the PR's own files. What the shipped CI templates now enforce under a strict target (ado strict mode --base origin/<target> is asked first; an unreadable config, or any exit other than 0 and 2, fails the job): a PR with no story id (no AB# in the GitHub title or body, no id in the Azure source branch, read with the target's branch_prefix) fails instead of skipping the gate; ado strict check <id> --phase pr --head <head sha> --base origin/<target> runs after the gate in a step or command without ADO_TOKEN (the check is local), lists rule ids only (never the ledger's text) in the PR comment, and fails the job on any non-zero exit; and the link-on-merge templates fail the job when the strict done check refuses (the refused story is not moved by the optional transition; the others are), with strict done refused: <rule ids> instead of the misleading check ADO_TOKEN and config warning (the GitHub one checks out the exact merged commit, merge_commit_sha, at full depth). With an advisory or absent target config the templates behave as in v0.2. The gate, branch-guard and strict re-run GitHub workflows ran once in a private test repository on hosted runners (2026-11-08); the Azure DevOps agents have not been run in this project's environment (billing), and ado-link-on-merge.yml has not run in a consumer repository: that template logic is covered by bash -n and real-bash tests with a fake ado, not by a hosted run. The first PR that introduces strict mode is judged by its own config, because the target has none yet (or an advisory one), and with --base it carries the two trust notes (trust-introducing PR: review ado.stack.json as code, and for a first lockfile trust-introducing PR: review ado.kits.lock.json as code) in the strict check warnings and the gate comment; from the merge on, the target's config applies. A PR that adds strictness (its config is strict, the target's is advisory) is judged strict by its own file.

Optional CI re-run job (ado-strict-verify.yml), the Azure Pipelines file SHIPPED UNRUN, the GitHub file run once in a test repository. .github/workflows/ado-strict-verify.yml and pipelines/ado-strict-verify.yml re-run ado strict verify <id> --no-record --base origin/<target> on the PR: the red commit must fail and the green commit must pass, with the test command taken from the target branch's config. The job declares no secret and maps no token (contents: read only, credentials not persisted, full-depth checkout) and does nothing unless the target branch's config is strict. Plainly: it re-runs the tests at the recorded commits under the target branch's command; it fails while an l2 or test-command override is in force unless allow-override is set; it cannot be satisfied by hand-written records; it does not show a test is meaningful (the PR still writes the tests at those commits; the fidelity verdicts and the human review gate cover that). It judges the PR head commit (as the gate's --head). An override in force skips the run, so ado strict verify --no-record exits 2 with the finding override-in-force (naming the override ids) unless --allow-override is passed; the template input allow-override (default false) adds that flag. On Azure Pipelines the parameter is allowOverride. It runs your test command on the PR's code: there is no secret to steal, but a hostile PR can still run arbitrary code on the runner, so call it on pull_request only (never pull_request_target), keep approval for fork pull requests and use ephemeral runners. It is shipped unrun: Actions and hosted agents are billing-blocked here, so it is covered by structural pins, bash -n and real-bash tests with a fake ado, not by a hosted run. See docs/ci-github.md and docs/ci-azure-pipelines.md.

Security note: the test command is code from your project. ado strict verify runs strict.test_command at one commit in a temporary checkout: a throwaway git clone --shared --no-checkout in a fresh directory outside the repo (origin removed, never fetched, repository hooks off), so it shares no config, hooks or index with your repo, and the whole directory is removed afterwards, even on failure, timeout or Ctrl-C. Every git call and the command get a scrubbed environment: only PATH, LANG, LC_* (the 13 standard POSIX locale names only), TERM, TMPDIR, VIRTUAL_ENV, JAVA_HOME, GOPATH, NODE_PATH, GOROOT, FLUTTER_ROOT, DOTNET_ROOT, ANDROID_HOME, ANDROID_SDK_ROOT and RUSTUP_HOME are passed (the six SDK locations only when set to an absolute path without control characters; no GIT_* from the parent, no global git config, no prompts; the list is fixed in code and a profile cannot add names), CARGO_HOME, GRADLE_USER_HOME and PUB_CACHE are never passed (they can hold credentials), HOME is an empty temporary directory, and any name ending _TOKEN, _PAT, _SECRET, _KEY, _PASSWORD or _CREDENTIALS, ADO_TOKEN, GH_TOKEN, GITHUB_TOKEN, AZURE_DEVOPS_EXT_PAT, SYSTEM_ACCESSTOKEN, SSH_AUTH_SOCK and AWS_* are dropped. It has no stdin, runs in its own process group killed at strict.test_timeout, and its output is never returned or logged (line counts only, kept in constant memory). The recorded seconds stop when the command exits, not when its output pipes close. Global and system git config are ignored, so Git LFS filters do not run and LFS files are checked out as pointer files: a test that needs the real LFS content cannot pass here. This is hygiene, not a sandbox: the command still has your user's filesystem and network access, so it can read or write files outside the checkout (including your repo and home directory) and read or change its own checkout's .git. A process that calls setsid escapes the group kill, and if it keeps the output pipes open the runner stops waiting for them 10 s after the command ends. CI must run it without secrets: check out with persist-credentials: false (the shipped workflows do) and run the test command in a job where no step holds secrets. Hiding HOME hides default lookups only: see "Not a sandbox" in docs/configuration.md.

What this does and does not do

Read this before you rely on the stack and kit checks. They are guard rails for a team that reviews its pull requests, not a lock on a machine.

It will:

  • detect your stack from the files committed at HEAD and show the evidence (ado stack detect);
  • keep one reviewable profile, ado.stack.json, in which every command, convention and definition-of-done item cites a source or says unverified (read each why the preview prints too: the unverified count is a lower bound, see docs/stack-kits.md);
  • run, in strict mode, only the test command string a human approved with ado stack approve --apply, in a throwaway clone with a reduced environment;
  • refuse, in strict mode, an unknown or unprofiled stack, a profile nobody approved, and a kit nobody pinned or one that changed after it was pinned (stack-profile-*, stack-unprofiled, kit-unpinned, kit-changed).

It will not:

  • install a kit (it prints specify extension add <id> for you), fetch a web page from the CLI, or decide your stack silently;
  • vouch that a cited page says what the profile claims: the CLI never fetches a URL, and you are the check at approval;
  • run your lint, build or security commands, or any org_only command that needs a live org, a server or credentials, on its own;
  • sandbox your tests. They are your code and, in a pull request, the PR's code: the throwaway clone and the reduced environment are hygiene, not a sandbox (docs/configuration.md);
  • stop a determined agent or person from editing files by hand. Every check here is process enforcement, not a security boundary (a terminal check stops accidents, an approval is a record, a pin says someone looked). The binding enforcement is the strict check CI re-runs against the target branch's profile and lockfile, and your branch rules on those files.

Boundaries, plainly:

  • Azure DevOps Boards only. The tracker is Azure DevOps Boards (code on Azure Repos or GitHub). Jira and GitHub Issues are not supported. There is no adapter interface: board access is a set of modules built on one Azure DevOps client (client, workitems, comments, questions, decisions, attachments, push, done, prs), so another tracker would mean reimplementing them. The stack detection, the profile and kit pinning make no tracker calls; no adapter is built.
  • Stack kits are optional. Without a kit, core Spec Kit runs each phase. The profile works with or without one.
  • Third-party kits are code the agent runs. The kit rules (kit-unpinned, kit-changed) accept only kits a human reviewed and pinned with ado kits pin, and refuse a kit that changed since. The pin records a review; the automated scan behind it is a heuristic aid, not a verdict.
  • Spec Kit engine limits. Spec Kit's own manifest_hash covers only a kit's extension.yml, not its command files, which is why this project hashes the kit directory and the agent copies itself. A kit installed with specify extension add --dev cannot be pinned. specify extension search prints text with no JSON, so kit facts come from the catalog cache files. The workflow engine's shell step defaults to 300 s, so strict-verify sets timeout: 7200. CI sees git objects, not what an agent runs, so agent copies of a kit are checked only on a machine that has them.

Human in the loop

The rules live in one file, rules/hitl.md, linked from every command. In short:

  • Reading ADO and writing local spec or ledger files is free.

  • Any ADO mutation (create, update, state, comment, link, attach), opening a PR, pushing a branch or commenting on a PR needs the exact change shown and an explicit yes. One yes covers one previewed batch.

  • Tokens are never requested, accepted, echoed, logged or stored by the agent.

  • Customer or member data never goes into ADO fields, comments, URLs, ledgers or attachments.

  • Who may approve (comment mode). Three config keys, approvers (0 to 20 ADO identity ids), approval ("terminal", the default, or "comment") and unattended, are read only from the target branch, never from a pull request's own checkout: a PR that edits them changes nothing until it is merged. The agent never runs as an admin or approver: it runs as a Contributor without the "Bypass rules on work item updates" permission, approvers are separate human identities (a separate account, no approver PAT in the agent's environment) and the CI service identity is never an approver. ado doctor fails when an approver is the token's own identity and its bypass row fails when the token can bypass rules. Comment mode reads (/approve D<n>, /reject D<n>: note, /answer Q<n>: text or /approve <gate> <64 hex> as the first non-empty line of an approver's unedited comment; quoted text, the agent's own comments and comments carrying createdOnBehalfOf never count; comment mode is refused while the token identity can bypass rules or that cannot be read); ado decisions <id> --sync and ado questions <id> --sync act on the approvers' comments, and with approvers set ado done (and the CI close step) cross-checks every verdict of the decisions file against those comments (decisions-xcheck-*), so a hand-written validated line is refused (strict) or warned (advisory); and with approval: "comment" the five ADO applies (questions --post, push, decisions --post, pr create, branch --link) refuse unless a trusted approver commented /approve <gate> <hash> on the story, the hash covering that exact plan; done --apply, strict override, any --force and the single-item verbs are never approvable by comment. The unattended poller is described in docs/unattended.md. Details and residuals: configuration.

Three layers enforce this: type: gate steps in the ado-lifecycle workflow (preview, gate, apply for every board change and PR; command steps make no ADO writes there), dry-run-by-default batch verbs in the CLI, and the agent rules plus constitution articles. The rules govern the agent and the workflow: single CLI verbs (ado update, ado comment, ...) act immediately when a person runs them, and CI acts after a merge only as configured below.

CI

Both hosts get the same three checks: post the gate result on the PR, require the branch name to reference a work item, and comment on (and optionally transition) the story after merge. Closing the story on merge is opt-in: with close-story: true (closeStory: true on Azure Pipelines), after merge it attaches the completed ledger and moves the story to done_state; only if every DoD box is ticked. The gate fails a PR only for checks listed in gate.block (ac_traceability, assertion, ac_drift, open_questions, commits_without_story, open_decisions, rule_coverage, rule_drift); missing information never fails CI (with ac_traceability blocking, an AC row with no test does fail it; the exception is rule_drift, where ADO that cannot be read is a finding, rules-unreachable, in strict mode).

In CI the PR's own ado.config.json is untrusted: an invalid one (including any string with a control character) fails the gate (exit 3) instead of being skipped, and text the CI steps echo from it or from branch names is cut to one line with control characters replaced by spaces.

Security model and limitations

  • Token storage. ado setup stores the PAT in the macOS Keychain when available; elsewhere, and as the macOS fallback, in ~/.azdo/<org>.token, a plaintext file created with mode 0600. The CLI warns when that file is group- or world-readable. On macOS the token is passed briefly as an argument to the security tool, so a local ps could see it for an instant; this comes from staying stdlib-only. Avoid the file store on shared hosts. $ADO_TOKEN takes precedence over both stores, which is how CI supplies the token.
  • Command output can contain sensitive data. ado get and ado query print full work-item JSON (title, description, custom fields). In CI that lands in run logs, so control log access and retention and prefer narrow queries.
  • The attachment allowlist checks file types, not contents. Only extensions in attachments_allow (default .md, .svg, .txt) can be attached, and never through a symlink; anything else aborts. Sensitive data pasted into an allowed file, or script inside an .svg, is not detected.
  • The ledger copies the story as verbatim text (ADO HTML converted to plain text). ado dod copies the acceptance criteria, description and repro steps from ADO without scanning them. Read section 1 before committing it.
  • A partial attach can leave an orphaned upload. If a file uploads but linking it fails, ADO keeps the unlinked upload (reported under failed, exit 1). Re-run to retry; the orphan is harmless but not cleaned up.
  • No Windows credential store yet. Windows uses the same plaintext file (%USERPROFILE%\.azdo\<org>.token), but mode 0600 has no effect there; the file is protected only by your user profile's access control.

How this compares to other ADO extensions

The Spec Kit community catalog lists two other Azure DevOps extensions. Per their catalog descriptions:

  • azure-devops (Azure DevOps Integration) syncs user stories and tasks to Azure DevOps work items using OAuth authentication.
  • maqa-azure-devops (MAQA Azure DevOps Integration) is an Azure Boards integration for the MAQA extension: it populates work items from specs, moves User Stories across columns as features progress, and ticks child Tasks in real time.

spec-kit-ado covers a different scope: the full lifecycle from story to Done (ledger, routed phases, child Tasks, gate, multi-plane review, PR, close), with an approval step before every board or PR change and both GitHub and Azure Repos/Pipelines as hosts. If you only need work-item sync, one of the extensions above may be a better fit.
