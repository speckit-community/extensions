AI Did It

A·I·DID·IT is an agile expansion pack for GitHub Spec Kit. Spec Kit gives your coding agent a spec-driven loop: specify, plan, tasks, implement (Spec Kit). AI Did It wraps that loop in a whole delivery lifecycle. A simulated agile team (product owner, architect, QA, DevSec, DevOps) reviews the work. A panel of software practitioners makes the decisions you would otherwise be paged for. You keep exactly one job: clicking merge.

Assemble the lanes. Ideate the work. Draft the bet. Iterate to build it. Deliver it to users. Investigate what actually happened. Tidy what you learned.

🦆 Why a Duck, Why a Lifecycle

Hand an agent a whole feature in one long conversation and the same things go wrong every time. The context fills up and quality slips quietly (Liu et al.; Hong, Troynikov & Huber). Early decisions get forgotten. The tests end up agreeing with the code instead of checking it. And you get interrupted for every judgement call.

AI Did It answers each of those with a published practice:

ProblemPracticeStanding on
One context doing everythingLanes. Each work item runs as a chain of six short, single-purpose sessions joined by a written handoff note.Small batches, continuous delivery
Endless revise loopsLoop budgets. Clarify and analyze run at most 3 rounds, exit early when nothing CRITICAL or HIGH remains, then the panel rules once.Timeboxing
You as the bottleneckThe practitioner panel. Beck, Fowler, Farley, Dahan and Martin, each position web-cited and checked, decide what you would normally be asked.Independent judgement, anchoring
Tests that agree with the codeTDD with kill tests. Every guard needs a recorded mutation that turns it red, and a run that shows it green.Beck, mutation testing
"It merged, so it works"Investigate. The null hypothesis is that the delivery failed; the change is checked against the running system.Dijkstra, Popper
Lessons that evaporateRetros that act. Every lane link before Tidy ends with a retro, and Tidy turns its actions into new work items.Kerth, Deming

The duck is a nod to rubber-duck debugging (Hunt & Thomas): explaining your work out loud to something that listens. Here, the duck listens, then files a PR.

🚀 Quick Start, Quacking

You need Python 3.11 or later, uv, git, and a coding agent that Spec Kit supports (Claude Code, GitHub Copilot, Gemini CLI, Codex, Cursor, opencode and more).

uv tool install git+https://github.com/RubberDuckEngineering/rubber-duck-engineering-ai-did-it

That one command installs the aididit CLI and Spec Kit (specify-cli 1.3+) into the same tool environment. Then, in your project:

aididit doctor

aididit install --integration claude

install runs specify init if the folder is not a Spec Kit project yet, adds the pack, seeds a starter Kanban board at .specify/aididit/board.md, and registers the single-lane workflow. Running it again upgrades in place and keeps your config and your board. The CLI page draws every step.

Now talk to your agent:

You want to…Say
Turn an idea into a well-formed story/speckit.aididit.ideate I want users to export their data
Ship everything in the Ready column"Agents Assemble" (or /speckit.aididit.assemble)
Walk one item through every stage, approving each hand-offspecify workflow run aididit-lane
Run one stage by hand/speckit.aididit.draft, /speckit.aididit.iterate, …
Ask a teammate/speckit.aididit.architect, /speckit.aididit.qa, …

Command syntax depends on your agent. Claude Code shows them as /speckit-aididit-ideate; Spec Kit renders the right form for each agent at install time. Every command lives in the pack's own speckit.aididit.* namespace, so nothing collides with Spec Kit's core commands or another extension's.

🔤 The Lifecycle at a Glance

StageCommandWhat happens
AAssemblespeckit.aididit.assembleRead the board, group items by file overlap, start one lane per item, report.
IIdeatespeckit.aididit.ideateMode A (you): Socratic, one question at a time, cite-or-don't-suggest. Mode B (a lane): interrogate an accepted item's premises, scope and testability before any drafting.
DDraftspeckit.aididit.draftspecify → clarify loop → plan → tasks → analyze loop → team review. Produces spec.md, plan.md, tasks.md, contracts and ADRs.
IIteratespeckit.aididit.iterateTDD red/green/refactor, Conventional Commits, push, open the PR, post-implementation analyze.
DDeliverspeckit.aididit.deliverPanel review and bot review on the PR, resolve threads, drive checks green, stop for the merge.
IInvestigatespeckit.aididit.investigateVerify the merged change against the running system; verdict CLEAR / DEGRADED / REGRESSED / UNVERIFIABLE.
TTidyspeckit.aididit.tidyClose the item, triage the board, turn retro actions into new work.

The agent-facing reference is shared/lifecycle.md.

On top of the roles sits the practitioner panel. It is convened fresh for each decision. A position without a verified citation is labelled [Inference] and cannot decide anything on its own. The personas simulate published positions. None of the practitioners has reviewed or endorsed this project.

⚙️ Configuration

.specify/extensions/aididit/aididit-config.yml is created on first install and kept on upgrade:

KeyDefaultMeaning
board.providermarkdownmarkdown (a Kanban file in the repo), github (Issues via gh), or jira (needs an Atlassian MCP server)
lanes.runnerinlineinline (current session runs each link, works with every agent), claude (detached headless sessions), claude-remote (sessions you can watch and steer from Claude Desktop or mobile)
lanes.max_parallel3Lane cap for one Assemble run, a work-in-progress limit (Little)
panel.practitionersBeck, Fowler, Farley, Dahan, MartinWho sits on the panel
loops.clarify_max_rounds / loops.analyze_max_rounds3 / 3Loop budgets
delivery.mergehumanauto turns on Full Auto Mode: the Deliver link merges its own PR once every check is green and every thread resolved

Project-owned state (the board, retros, lane ledgers) lives in .specify/aididit/, so it survives upgrades and uninstalls. Lane ledgers are git-ignored working state; retros are committed on each lane's branch, and the board file is yours to commit. No lane commits it, so parallel PRs never conflict over it.

💻 The CLI

CommandDoes
aididit install [PROJECT] [--integration AGENT] [--no-init]Initialise Spec Kit if needed, add or upgrade the pack, seed the board
aididit uninstall [PROJECT] [--keep-config]Remove the pack and lane workflow; keep .specify/aididit/
aididit doctorCheck Python, Spec Kit, git (required) and gh, claude (optional)
aididit --versionPrint the version

Already living in Spec Kit and prefer its own tooling? Run specify extension add aididit --from <zip URL> with the aididit-vX.Y.Z.zip asset of the latest release, or clone this repo and run specify extension add --dev src/aididit/pack. Either way, the first stage that reads the markdown board creates .specify/aididit/board.md from the starter template if it is missing, and never overwrites one that is there.

🗂️ Repository Layout

Everything is organised by feature, not by technical layer (Bogard):

src/aididit/
├── cli.py                    # argument parsing only; routes verbs to feature slices
├── features/
│   ├── install/              # init → add pack → seed state → register workflow
│   ├── uninstall/
│   └── doctor/
└── pack/                     # the Spec Kit extension, copied to .specify/extensions/aididit/
    ├── extension.yml
    ├── aididit-config.template.yml
    ├── stages/<stage>/       # one folder per lifecycle stage
    ├── personas/<role>/      # one folder per simulated teammate
    ├── shared/               # lifecycle, lane contract, panel, board adapters, retro, disciplines
    ├── scripts/              # lane spawners (bash + PowerShell)
    ├── templates/board.md
    └── workflows/aididit-lane.yml
docs/                         # the field guide (for people); the pack is for agents
tests/                        # mirrors the slices, plus pack, diagram, link, PII and end-to-end suites
tools/                        # maintainer tools: the release zip, the commit identity and time-zone checks, and the range CI checks

🧪 Developing

uv sync

uv run pytest

The suite has six layers:

  • Unit tests cover each feature slice at 100% branch coverage.
  • Pack contract tests check that every cross-reference, command token and config key in the prompts resolves.
  • Diagram tests hold every Mermaid diagram to the house style and re-measure its contrast against GitHub's light and dark themes.
  • Link tests resolve every relative link and every citation anchor.
  • PII tests keep personal data out of the repo, and tools/check_commit_identity.py keeps it out of commit authors and committers. tools/check_commit_timezone.py holds commits made as the project to UTC, so their dates say when, never where. CI runs both over the commits a pull request or push brings (tools/commit_range.py), so a commit on main is judged once, when it lands.
  • End-to-end tests drive the real specify against a throwaway project.

See CONTRIBUTING.md for the rules every change follows. They come from the pack itself: TDD, Conventional Commits, and guards that can both fail and pass. Anyone can open an issue; pull requests are open to collaborators, and every change to main needs a maintainer's approval.
